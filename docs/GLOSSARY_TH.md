## 2. การวัดผล

**wall clock / เวลานาฬิกาจริง**
เวลาที่ผ่านไปจริงๆ วัดด้วยนาฬิกาบนผนัง ต่างจาก "เวลาที่ CPU ใช้" ซึ่งบวกกันข้ามเธรดได้เกินเวลาจริง
งานที่รันสองเธรดพร้อมกันเธรดละ 10 วินาที กิน CPU 20 วินาที แต่ wall clock แค่ 10

**`realtimeRatio` ⭐ ตัวชี้วัดหลักของโปรเจกต์**
`เวลาที่ใช้ประมวลผล ÷ ความยาวคลิป`
- **< 1.0** = ประมวลผลเร็วกว่าที่กล้องถ่าย → ตามทันการถ่ายสด คิวไม่บวม
- **= 1.0** = พอดีเป๊ะ
- **> 1.0** = ช้ากว่าที่ถ่าย → ถ่ายสดนานๆ คิวจะบวมจนต้องหยุดกล้อง

v0.1.3 = 2.196 (ช้ากว่าสองเท่า) → **v0.1.4 = 1.010**

**`sharePercent`**
สัดส่วนที่ stage หนึ่งกินไป เทียบกับ wall clock จริง
**รวมกันได้เกิน 100% โดยตั้งใจ** เพราะ producer กับ consumer ทำงานทับซ้อนกัน — ส่วนที่เกิน 100% คือมูลค่าของการทำงานขนาน (TC-12 รวมได้ ~280%)

**percentile · p25 / p50 / p75**
เรียงข้อมูลจากน้อยไปมากแล้วดูว่าค่าที่ตำแหน่ง N% คือเท่าไหร่
**p50 = ค่ากลาง (median)** — ทนต่อค่าสุดโต่งกว่าค่าเฉลี่ย
ใช้กับ sharpness เพราะการกระจายเบ้มาก (chunk เดียวมีตั้งแต่ 15 ถึง 723)

**avg vs max**
`avg` บอกต้นทุนปกติ · `max` บอกกรณีแย่สุด
ตัวอย่างที่ต่างกันสุดขั้ว: GPU มี `detect` avg 60 ms แต่ **max 2,465 ms** — เฟรมแรกจ่ายค่า warm-up คนเดียว

**invariant**
ความสัมพันธ์ที่ต้อง**เป็นจริงเสมอ** ไม่ว่าจะรันกี่ครั้ง ใช้ตรวจว่าโค้ดยังทำงานถูกไหมโดยไม่ต้องดูโค้ด
ของเรา: `jpeg_argb_full n` = candidates + tooSoft + roiInvalid — TC-12 ได้ `541 = 293 + 248 + 0` เป๊ะ **ถ้าเลขนี้ไม่ตรงเมื่อไหร่ แปลว่ามีอะไรพัง**

**baseline**
ตัวเลขอ้างอิงก่อนแก้ ไว้เทียบว่าแก้แล้วดีขึ้นจริงไหม · เปลี่ยนโค้ดแล้วต้องวัด baseline ใหม่

**การทดลองตัวแปรเดียว (single-variable experiment)**
เปลี่ยนทีละอย่างแล้ววัด ถ้าเปลี่ยนสองอย่างพร้อมกันจะแยกไม่ออกว่าผลมาจากอะไร
เราพลาดข้อนี้ครั้งหนึ่ง: แก้ decode พร้อมกับขยายคิวจาก 2 เป็น 6 — โชคดีที่ข้อมูลบอกทีหลังว่าคิวไม่ได้ทำอะไรเลย

**ตัวแปรกวน (confound)**
สิ่งที่มีผลต่อการวัดโดยที่เราไม่ได้ตั้งใจวัดมัน
ตัวใหญ่ที่สุดของเราคือ **DVFS** — เครื่องช้าลง 25% ระหว่างรัน ทำให้ chunk ท้ายๆ ดูช้าทั้งที่งานเท่ากัน

**deterministic / ทำซ้ำได้**
รันข้อมูลชุดเดิมสองครั้งได้ผลเหมือนกันเป๊ะ
`enableTracking()` ของ ML Kit ทำให้ผลไม่ deterministic (ผลขึ้นกับเฟรมก่อนหน้า) จึงถูกถอดออกใน v0.1.4 — เพราะการทดลองทุกอย่างหลังจากนี้ต้องการความสามารถนี้

**regression**
ของที่เคยใช้ได้แล้วพังเพราะการแก้อย่างอื่น

**smoke test**
ทดสอบหยาบๆ แค่ "เปิดแล้วไม่พัง" ไม่ได้วัดตัวเลข — ใช้กันของพัง ไม่ได้ใช้วัดผล

**repro (reproduction)**
ขั้นตอนที่ทำให้บั๊กเกิดซ้ำได้ตามสั่ง · **ไม่มี repro = ยังไม่ยืนยันว่าเจอต้นเหตุ** แม้จะแก้ไปแล้ว

## 3. ฮาร์ดแวร์และการเร่งความเร็ว

**CPU / GPU / NPU**
- **CPU** — ชิปประมวลผลทั่วไป ทำได้ทุกอย่างแต่ไม่ได้เก่งเรื่อง AI เป็นพิเศษ
- **GPU** — เดิมทำกราฟิก แต่คำนวณขนานเก่ง จึงเอามารัน AI ได้
- **NPU** (Neural Processing Unit) — ชิปที่ออกแบบมารัน AI โดยเฉพาะ เร็วและกินไฟน้อยกว่า แต่**มีเฉพาะบางรุ่น** ของเราคือ Snapdragon เท่านั้น

**DVFS ⭐ (Dynamic Voltage and Frequency Scaling)**
กลไกที่ระบบ **ลดความเร็วสัญญาณนาฬิกาของ CPU ลงเอง** เพื่อประหยัดไฟและกันเครื่องร้อน

ทำไมสำคัญกับเรา: TC-12 วัดได้ว่าใน 4 นาทีครึ่ง ความถี่ตกจาก **2,918,400 → 1,651,200 kHz (−43%)** และงานเดียวกันช้าลง 25% — **โดยที่ API วัดอุณหภูมิของ Android รายงานว่า "ปกติ" ตลอด**

แปลว่า: **ตัวเลขที่วัดตอนต้นกับตอนท้ายของ session เดียวกัน เทียบกันตรงๆ ไม่ได้** และการเทียบสอง build ต้องดูก่อนว่า drift ใกล้กันไหม

**thermal throttling**
ญาติสนิทของ DVFS — เครื่องร้อนแล้วลดความเร็วเพื่อกันไหม้ · Android มี API บอกระดับ (`OK` / `Warm` / `Hot` …) แต่**ของเรารายงาน `OK` ตลอดขณะที่ความถี่ตกไป 43% แล้ว** จึงต้องวัดเองด้วย `DvfsProbe`

**clock / frequency (kHz)**
ความเร็วสัญญาณนาฬิกา · 2,918,400 kHz = 2.92 GHz

**delegate**
ตัวกลางที่บอก framework ว่า "งานนี้ไปรันบนชิปไหน" · `GpuDelegate` = ส่งไปรันบน GPU

**warm-up**
ต้นทุนครั้งแรกที่จ่ายก่อนของจะวิ่งเต็มความเร็ว
GPU ต้องคอมไพล์ shader ก่อนใช้ → **เฟรมแรกกิน 2.5 วินาที** เทียบเฟรมถัดๆ ไป 60 ms

**JIT (Just-In-Time compilation)**
Java/Kotlin ตอนเริ่มรันจะ "ตีความ" ทีละคำสั่งซึ่งช้า พอโค้ดถูกเรียกบ่อยพอถึงจะคอมไพล์เป็นภาษาเครื่อง
**เป็นเหตุให้เครื่องมือวัด DVFS ของเรามีบั๊ก** — ค่าครั้งแรก 6.2 ms เทียบค่าปกติ 3.0 ms เพราะครั้งแรกยังไม่ถูกคอมไพล์

**LiteRT**
ชื่อใหม่ของ **TensorFlow Lite** (Google เปลี่ยนชื่อปี 2024) — framework รันโมเดล AI บนมือถือ

**ML Kit**
ชุดโมเดล AI สำเร็จรูปของ Google (ตรวจใบหน้า อ่านข้อความ ฯลฯ) ใช้ง่ายแต่ปรับแต่งไม่ได้ · ของเราใช้เป็นค่าเริ่มต้นและเป็นตัวสำรอง

**QNN / Qualcomm AI Hub**
ชุดเครื่องมือของ Qualcomm สำหรับรันโมเดลบน NPU ของ Snapdragon · โมเดล `face_det_lite` ของเราโหลดมาจากที่นี่

**quantization / w8a8**
ลดความละเอียดตัวเลขในโมเดลจากทศนิยม 32 บิตเหลือจำนวนเต็ม 8 บิต เพื่อให้เล็กลงและเร็วขึ้น
**w8a8** = weight 8 บิต, activation 8 บิต · แลกมาด้วยความแม่นยำที่ลดลงนิดหน่อย

**NDK / JNI**
- **NDK** — ชุดเครื่องมือเขียน Android ด้วยภาษา C/C++ (เร็วกว่า Kotlin แต่เขียนยากและพังง่ายกว่า)
- **JNI** — สะพานเชื่อมระหว่าง Kotlin/Java กับ C/C++

**sysfs**
ระบบไฟล์เสมือนของ Linux ที่ให้อ่านสถานะฮาร์ดแวร์เหมือนอ่านไฟล์ · เราอ่านความถี่ CPU จาก `/sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq` — **บางเครื่องไม่ยอมให้อ่าน** จึงเป็นตัวสำรองไม่ใช่ตัวหลัก

## 4. วิดีโอและภาพ

**codec / MediaCodec**
ตัวเข้ารหัส-ถอดรหัสวิดีโอ · `MediaCodec` คือ API ของ Android ที่เข้าถึงชิปถอดรหัสวิดีโอโดยตรง (เร็วกว่าถอดด้วย CPU มาก)

**YUV420 / NV21 / ARGB_8888 — รูปแบบการเก็บสีของภาพ**
- **YUV420** — แยกความสว่าง (Y) ออกจากสี (U,V) แล้วเก็บข้อมูลสีแค่ 1/4 เพราะตามนุษย์ไวต่อความสว่างมากกว่าสี · เป็นสิ่งที่ตัวถอดรหัสวิดีโอคายออกมา
- **NV21** — YUV420 แบบเรียงข้อมูลเฉพาะทาง (V มาก่อน U) ที่ Android ต้องการก่อนเข้ารหัส JPEG
- **ARGB_8888** — เก็บทุกพิกเซลเป็น 4 ไบต์ (โปร่งใส/แดง/เขียว/น้ำเงิน) **กินที่มากที่สุด** ภาพ 4K = 33 MB ต่อภาพ

การแปลง YUV420 → NV21 คือ `yuv_nv21` ซึ่งกิน **61.6% ของเวลาทั้งงาน** — คอขวดตัวใหญ่ที่สุดที่เหลือ

**JPEG · DCT · entropy coding (Huffman)**
JPEG บีบภาพสองขั้น:
1. **DCT** (Discrete Cosine Transform) — แปลงภาพเป็นคลื่นความถี่แล้วทิ้งรายละเอียดที่ตามองไม่เห็น
2. **entropy coding / Huffman** — บีบข้อมูลที่เหลือแบบไม่สูญเสีย

**ทำไมต้องรู้:** เวลาย่อภาพตอนถอดรหัส ขั้น Huffman **ยังต้องไล่ทั้งไฟล์เหมือนเดิม** ย่อได้แค่ขั้น DCT — จึงเป็นเหตุที่ `inSampleSize=2` ให้พิกเซลน้อยลง 4 เท่าแต่เร็วขึ้นแค่ 36%

**`inSampleSize`**
ตัวเลือกของ Android ที่บอกว่า "ถอดรหัส JPEG นี้โดยย่อลง N เท่าเลย" ประหยัดกว่าถอดเต็มแล้วค่อยย่อ · รับเฉพาะกำลังของ 2 (1, 2, 4, 8)

**bilinear / aliasing**
- **bilinear** — วิธีย่อภาพที่เฉลี่ยจากพิกเซลข้างเคียง 2×2
- **aliasing** — ความผิดเพี้ยนที่เกิดเมื่อย่อเกิน 2 เท่าในขั้นเดียว เพราะมันข้ามพิกเซลไปเลย ไม่ได้เฉลี่ย · รายละเอียดที่หายไปคือสิ่งที่ตัวตรวจจับใบหน้าใช้พอดี **(เราเคยตั้งสมมติฐานว่านี่คือสาเหตุที่หาหน้าไม่เจอ แต่วัดแล้วพบว่าผิด)**

**PTS (Presentation Time Stamp)**
เวลาประทับบนแต่ละเฟรมว่า "เฟรมนี้ต้องแสดงที่วินาทีที่เท่าไหร่" · เราใช้ตั้งชื่อไฟล์และเรียงลำดับตอนคัดเลือก

**keyframe / sync frame / GOP**
- **keyframe** — เฟรมที่เก็บภาพเต็ม ไม่ต้องพึ่งเฟรมอื่น
- เฟรมอื่นเก็บแค่ "ต่างจากเฟรมก่อนหน้าตรงไหน" จึงเปิดกลางคันไม่ได้
- **GOP** (Group of Pictures) — ช่วงตั้งแต่ keyframe หนึ่งถึงตัวถัดไป
**การตัดวิดีโอต้องตัดที่ keyframe เท่านั้น** ไม่งั้นไฟล์ที่ได้จะเละตอนต้น

**remux vs re-encode**
- **remux** — ย้ายข้อมูลวิดีโอไปใส่ไฟล์ใหม่ **โดยไม่ถอดรหัส** เร็วมากและไม่เสียคุณภาพ · ของเราตัด 1.93 GB เสร็จใน 17 วินาที
- **re-encode** — ถอดรหัสแล้วเข้ารหัสใหม่ ช้าและเสียคุณภาพ **เราไม่ทำ**

**MediaExtractor / MediaMuxer**
- **Extractor** — ตัวอ่านข้อมูลออกจากไฟล์วิดีโอ
- **Muxer** — ตัวเขียนข้อมูลลงไฟล์วิดีโอ
ทั้งคู่จองหน่วยความจำระดับระบบ **ถ้าไม่ปิดจะรั่ว** (เป็นบั๊กที่เพิ่งแก้ไปในสปรินต์นี้)

**EXIF Orientation**
ข้อมูลกำกับในไฟล์ภาพที่บอกว่า "ภาพนี้ต้องหมุนกี่องศาตอนแสดง" · เขียนแท็กแทนการหมุนพิกเซลจริงจะประหยัดกว่ามาก — เป็นทางเลือกที่ยังไม่ได้ทำ (การหมุนภาพจริงกิน 14.4% ของเวลาทั้งงาน)

**bitmap · recycle**
- **bitmap** — ภาพที่ถอดรหัสแล้วอยู่ในหน่วยความจำ
- **recycle** — คืนหน่วยความจำทันทีโดยไม่รอ garbage collector · จำเป็นเพราะภาพ 4K ใบละ 33 MB ลืมคืนไม่กี่ใบก็แอปตาย

**HardwareBuffer / `ImageFormat.PRIVATE`**
วิธีส่งภาพระหว่างชิปโดยไม่ผ่าน CPU เลย — เร็วที่สุดในทางทฤษฎี **แต่เราลองแล้วล้มเหลวหนึ่งครั้ง** และตอนนี้มีทางที่ถูกกว่าและเสี่ยงน้อยกว่ารออยู่ จึงเก็บไว้เป็นทางสุดท้าย

**FHD / UHD / 4K**
- **FHD** = 1920×1080 (1080p)
- **UHD / 4K** = 3840×2160 — พิกเซลมากกว่า 4 เท่า

## 5. โครงสร้าง pipeline

**Worker 1 / Worker 2**
- **Worker 1** — ผลิต chunk (ถ่ายสด = อัดวิดีโอ · import = ตัดไฟล์)
- **Worker 2** — สุ่มเฟรมจาก chunk → ตรวจหน้า → คัด → เซฟเป็น JPEG

**chunk**
ไฟล์วิดีโอย่อยขนาด ~50 MB ที่ระบบตัดออกมาเพื่อทยอยประมวลผล · **เป็นไฟล์ชั่วคราว ไม่ใช่ของที่ส่งให้ลูกค้า**

**producer / consumer**
รูปแบบการทำงานที่แยกฝั่ง "ผลิต" กับ "บริโภค" ออกจากกันด้วยคิว เพื่อให้ทั้งสองฝั่งทำงานพร้อมกันได้
ของเรา: **producer** = ถอดรหัสวิดีโอ · **consumer** = ตรวจหน้า (2 ตัว)
ก่อน v0.1.4 ทั้งสองอย่างรันเรียงกัน เวลารวมจึงเป็น *ผลบวก* — หลังแยกแล้วกลายเป็น *ค่าที่มากกว่า*

**bottleneck / คอขวด**
ฝั่งที่ช้าที่สุด ซึ่งเป็นตัวกำหนดความเร็วรวมทั้งหมด **เร่งฝั่งอื่นไม่ช่วยอะไรเลย**
บทเรียนของเรา: เร่งการตรวจจับด้วย NPU ให้เร็วขึ้น 34% ได้เวลารวมคืนมาแค่ 4% เพราะคอขวดอยู่ที่ producer

**backpressure**
กลไกที่ให้ฝั่งที่ช้ากว่า "ดัน" ให้ฝั่งเร็วชะลอตัว เพื่อไม่ให้ของกองท่วมหน่วยความจำ
ของเรา: คิว chunk เต็ม (8 ใบ) → **กล้องหยุดหมุน chunk** และ splitter หยุดตัด

**queue / channel / capacity**
ที่พักของงานระหว่างสองฝั่ง · **capacity** = จุได้กี่ชิ้น
- **bounded** (มีขีดจำกัด) — เต็มแล้วผู้ผลิตต้องรอ · **ปลอดภัย** เพราะหน่วยความจำมีเพดาน
- **unbounded** — ใส่ได้ไม่จำกัดจนเครื่องตาย · **เราไม่ใช้**

**drain**
ช่วงจบงาน — รอให้ทุกอย่างในทุกคิวประมวลผลเสร็จหมดก่อนจะเขียนรายงานและปิด session
**เคยมีบั๊กที่ session จบโดยไม่เขียนรายงานเลยสองครั้ง** จึงมี watchdog คอยเช็คทุกวินาทีเป็นตาข่ายรอง

**sample interval**
ระยะห่างระหว่างเฟรมที่หยิบมาตรวจ · **120 ms** = หยิบประมาณ 8 เฟรมต่อวินาที (ไม่ใช่ทุกเฟรม)

**dedup window**
ช่วงเวลา **1 วินาที** ที่ระบบเลือกเก็บภาพคมสุดแค่ **3 ใบ** ป้องกันไม่ให้คนคนเดียวได้รูปซ้ำ 20 ใบ
**นี่คือเพดานจำนวนรูปจริงๆ** — สุ่มเฟรมถี่ขึ้นไม่ได้รูปเพิ่ม เพราะจำนวนหน้าต่างเท่าเดิม

**gate / threshold / ด่าน**
เกณฑ์ตัดสินว่าเฟรมผ่านหรือไม่ผ่าน (ขนาดหน้า · ความคม) · ตั้งสูงไป = ได้รูปน้อย · ตั้งต่ำไป = ได้รูปเบลอ

**candidate / kept / skipped**
- **candidate** — เฟรมที่ผ่านทุกด่านและถูกเซฟลงดิสก์แล้ว (TC-12: 293)
- **kept** — candidate ที่รอดจากการคัดซ้ำ ได้ขึ้นแกลเลอรีจริง (TC-12: 134)
- **skipped** — ถูกตัดทิ้ง (รวม 159 ใบที่เซฟแล้วโดนลบ)

## 6. การทำงานพร้อมกัน (concurrency)

**coroutine**
วิธีเขียนงานที่ทำพร้อมกันได้ในภาษา Kotlin โดยไม่ต้องจัดการเธรดเอง เบากว่าเธรดจริงมาก

**Dispatcher**
ตัวกำหนดว่า coroutine จะไปรันบนกลุ่มเธรดไหน
- **`Dispatchers.IO`** — งานที่รอ input/output (อ่านไฟล์ เน็ตเวิร์ก) · เธรดเยอะได้เพราะส่วนใหญ่นั่งรอ
- **`Dispatchers.Default`** — งานที่กิน CPU · เธรดจำกัดตามจำนวนคอร์
- **`Dispatchers.Main`** — เธรดที่วาดหน้าจอ · **บล็อกไม่ได้เด็ดขาด ไม่งั้นแอปค้าง**

**suspend**
ฟังก์ชันที่ "หยุดรอได้โดยไม่ยึดเธรดไว้" — ต่างจากการ sleep ที่ยึดเธรดทิ้งไว้เฉยๆ

**Channel**
คิวที่ coroutine ส่งของหากันได้อย่างปลอดภัย

**Mutex**
กุญแจที่ทำให้โค้ดช่วงหนึ่งมีเพียง coroutine เดียวเข้าถึงได้ในแต่ละครั้ง

**race condition**
บั๊กที่เกิดเพราะสองเธรดแตะข้อมูลเดียวกันในจังหวะที่ผิด · **เกิดไม่บ่อยและตามยาก** เพราะขึ้นกับจังหวะเวลา

**`@Volatile`**
คำสั่งบอกว่า "ตัวแปรนี้ต้องอ่านจากหน่วยความจำจริงเสมอ ห้ามใช้ค่าที่แคชไว้"
**ทำไมต้องมี:** แต่ละคอร์ของ CPU มีแคชของตัวเอง เธรด A เขียนค่าใหม่แล้วเธรด B อาจยังเห็นค่าเก่าไปเรื่อยๆ
ของเรา: watchdog อาจมองไม่เห็นว่า import จบแล้ว → session ไม่ปิด → ไม่เขียนรายงาน

**happens-before**
กฎที่รับประกันว่า "ถ้าเธรด B เห็นเหตุการณ์นี้ แสดงว่าต้องเห็นทุกอย่างที่เกิดก่อนหน้าด้วย" · ถ้าไม่มีกฎนี้เชื่อมสองเธรด ก็ไม่มีอะไรรับประกันลำดับที่เห็น

**atomic**
ตัวแปรที่การบวก/ลบเป็นการกระทำเดียวที่แทรกไม่ได้ · ถ้าใช้ `int` ธรรมดา สองเธรดบวกพร้อมกันจะได้ +1 แทน +2

**`CancellationException`**
ข้อยกเว้นพิเศษที่ระบบโยนเมื่องานถูกยกเลิก
**ห้ามจับแล้วกลืน** — ของเราเคยจับรวมกับข้อผิดพลาดทั่วไป ทำให้กดยกเลิก import แล้วระบบนึกว่า "ทำงานผิดพลาด" และไฟล์ที่เปิดค้างไม่ถูกปิด

**memory leak / resource leak**
จองแล้วไม่คืน · **file descriptor** = ช่องที่ระบบให้เปิดไฟล์ได้ มีจำนวนจำกัด รั่วมากพอแอปจะเปิดไฟล์ไม่ได้อีกเลย

## 7. การตรวจจับใบหน้า

**bounding box / bbox**
กรอบสี่เหลี่ยมรอบสิ่งที่ตรวจเจอ

**ROI (Region of Interest)**
บริเวณของภาพที่เราสนใจ · ของเราคือกรอบใบหน้า ใช้วัดความคมเฉพาะตรงนั้น ไม่วัดทั้งภาพ

**tile**
การหั่นภาพเป็นชิ้นๆ ก่อนป้อนโมเดล เพราะโมเดลรับขนาดตายตัว · ของเราหั่น 3 ชิ้น

**Laplacian variance**
วิธีวัดความคมของภาพ — ภาพคมมีขอบชัด ค่าความแปรปรวนจะสูง · ภาพเบลอค่าจะต่ำ
เกณฑ์ของเรา: **80** (FHD) / **65** (4K)

**subjectRatio**
ความสูงของใบหน้าเทียบกับความสูงของภาพ · **3.0%** ที่ 4K ≈ หน้าสูง 115 พิกเซลในภาพจริง

**recall / precision**
- **recall** — ของที่มีอยู่จริง เราเจอกี่ %  *(เราสนใจตัวนี้เป็นหลัก — พลาดนักวิ่งไม่ได้)*
- **precision** — ของที่เราบอกว่าเจอ ถูกจริงกี่ %

**IoU (Intersection over Union)**
วัดว่ากรอบสองอันซ้อนทับกันแค่ไหน (0 = ไม่ทับเลย · 1 = ทับสนิท) · ใช้เทียบว่าโมเดลสองตัวเห็นตรงกันไหม

**tracking / `trackingId`**
ฟีเจอร์ที่ให้หน้าเดิมมี ID เดิมข้ามเฟรม **เราถอดออกแล้ว** เพราะไม่มีใครใช้ ID เลย แต่มันทำให้ผลไม่ deterministic และเป็นต้นเหตุของ `roiInvalid`

**เหตุผลที่เฟรมถูกตัดทิ้ง (reject reasons)**

| ชื่อ | แปลว่า | TC-12 |
|--|--|--|
| `noSubject` | ไม่เจอหน้าเลยในเฟรมนี้ | 1,557 (68%) |
| `tooSmall` | เจอหน้าแต่เล็กเกินเกณฑ์ | 183 |
| `tooSoft` | หน้าใหญ่พอแต่เบลอเกินเกณฑ์ | 248 |
| `roiInvalid` | กรอบหน้าล้ำขอบภาพจนวัดความคมไม่ได้ | 0 |
| `decode_failed` | ถอดรหัสภาพไม่สำเร็จ | 0 |
