# Design Flow — ฉบับโปรเจกต์นี้

> เอกสารนี้ตอบ **Flow Design v1** ทีละข้อ ว่าข้อไหนทำ ข้อไหนไม่ทำ และเพราะอะไร
> เรียงหัวข้อตามสเปคต้นฉบับ เพื่อให้คนที่ถือสเปคนั้นอยู่เปิดเทียบได้ทันที
>
> **นี่ไม่ใช่ source of truth ของตัวเลข** — ค่าจริงอยู่ในโค้ด และเอกสารเชิงลึกอยู่ที่
> [PIPELINE_FLOW.md](./PIPELINE_FLOW.md) (pipeline) · [SEQUENCE_FLOW.md](./SEQUENCE_FLOW.md) (sequence + upload) · [PHASES.md](./PHASES.md) (สัญญากับ backend)
> ถ้าตัวเลขในนี้ขัดกับที่นั่น ให้เชื่อโค้ดก่อน แล้วมาแก้ที่นี่

## Video Pipeline

Flow Design v1 เป็น *camera pipeline* — ตัดสินใจตอนกดชัตเตอร์
ของเราเป็น *video pipeline* — บันทึกก่อน ตัดสินใจทีหลัง ทุกด่านจึงย้ายมาอยู่หลังการบันทึก

---

### 1. เปิดกล้อง

```
Use Cases        Preview + VideoCapture
                 (2 ตัว ไม่ใช่ 3 — ไม่มี ImageAnalysis, ไม่มี ImageCapture)
Preview ติดเมื่อ  เข้าหน้า Live
```

> ไม่ต้องรอกด Start — ตั้งกล้องบนขาตั้งและเล็งกรอบให้เสร็จก่อนเริ่มอัดได้

---

### 2. Preview

```
ใช้ทำอะไร        แสดงภาพสด + เล็งกล้อง
ไม่ใช้ทำอะไร      Detect
Overlay          Capture Zone · ค่ากล้อง · สถานะเครื่อง
```

> Preview ไม่เคยเข้าเส้นทางตัดสินใจเลย เป็นจอสำหรับคนอย่างเดียว

---

### 3. VideoCapture

```
ความละเอียด      1920x1080  หรือ  3840x2160
หมุนไฟล์ใหม่ทุก   50 MB
ที่ว่างขั้นต่ำ      2 GB
ตั้งค่าได้         เพดานชัตเตอร์ · ชดเชยแสง (EV)
```

> งานวิ่งเริ่มตี 4 ถ้าปล่อยให้ AE ยืดชัตเตอร์เอง นักวิ่งจะเบลอจนตกด่าน sharpness ทั้ง session

---

### 4. Video Queue

```
เข้าคิว           chunk ที่ปิดไฟล์แล้ว
ความจุ           8 chunk
คิวเต็ม           ตัวอัดหยุดรอ
```

> ยอมให้ backlog ยาว ดีกว่ายอมให้เฟรมหาย

---

### 5. Frame Sampling

```
ทำงานเมื่อ        ทีละ chunk ขณะที่กล้องยังอัดอยู่ (ไม่รอ session จบ)
Sample Interval  120 ms
Detect Bitmap    640 px กว้าง
Full-res decode  เฉพาะเฟรมที่ผ่านทุกด่านแล้ว
```

> decode ครั้งเดียวแล้วให้ทุก detector ใช้ภาพเดียวกัน — งานหนักที่สุดจ่ายทีหลังสุด

---

### 6. Detection

```
face_det_lite    640x480 grayscale · NPU   → ตอบว่า "ใคร"
ML Kit Pose      CPU                       → ตอบว่า "ตัวอยู่ในเฟรมครบไหม"
foot_track_net   640x480 · NPU             → ตอบว่า "ใครอยู่ตรงไหนบ้าง"
                                              ตัวเดียวที่เห็น ทุกคน ในเฟรม

เลือกเปิดได้ก่อน Start · เปิดพร้อมกันได้ทั้งสาม
เกตเป็น AND ไม่ใช่ OR — เปิดสองตัวแล้วผ่านตัวเดียว คือไม่ผ่าน
```

> จุดที่ต้องเปิดสองตัว คือจุดที่แต่ละตัวตอบคำถามที่อีกตัวตอบไม่ได้

---

### 7. Zone & Size Gate

```
ตำแหน่ง          จุดกึ่งกลาง subject ต้องอยู่ใน Capture Zone ที่ลากไว้เอง

ขนาดขั้นต่ำ       Face    0.035 (FHD) · 0.030 (4K)   ของความสูงเฟรม
                 Person  0.15
                 Torso   0.25

ขอบเฟรม          ต้องไม่ติดขอบ
```

> นักวิ่งที่ถูกตัดครึ่งขายไม่ได้ ต่อให้คมแค่ไหน

---

### 8. Sharpness Evaluation

```
วิธีวัด           Laplacian variance
วัดตรงไหน        บนใบหน้า ไม่ใช่ทั้งเฟรม
ย่อก่อนวัด        128x128 เสมอ
ขั้นต่ำ            80 (FHD) · 65 (4K)
```

> ย่อก่อนวัดทำให้ค่าเทียบกันได้ข้ามความละเอียด · ถ้าวัดรวมลำตัว ผ้าเรียบ ๆ จะเจือค่าจนอ่านไม่ได้ความ

---

### 9. Tracking

```
เก็บต่อคน         Track ID
                 Center Position
                 Velocity
                 Predicted Box
                 Last Seen
                 Kept Count

จับคู่รอบที่ 1     IOU กับ "กล่องที่ทำนายไว้" ไม่ใช่กล่องล่าสุด
จับคู่รอบที่ 2     ระยะห่างจุดกึ่งกลาง (เก็บตกที่รอบแรกจับไม่ได้)
```

> นักวิ่ง 3 m/s ที่ sample ทุก 120 ms เคลื่อนที่ไกลกว่าความกว้างตัวเอง
> IOU ดิบ ๆ จึงเป็น 0 และจะฉีกคนหนึ่งคนออกเป็น track ละเฟรม

### 10. Dedup ต่อคน

```
หน้าต่าง          1 วินาที
เก็บสูงสุด        3 เฟรม
นับต่อ            track ไม่ใช่นาฬิกา
```

> สองคนวิ่งผ่านในวินาทีเดียวกันได้คนละ 3 รูป ไม่ใช่แบ่งกัน 3 รูป
> วิธีเดิมทำให้คนหลังไม่ได้รูปเลย โดยระบบรายงานว่าปกติ

---

### 11. Quality Evaluation

```
Sharpness        0.40
Person Size      0.20
Center Score     0.15
Confidence       0.15
Edge Margin      0.10

จัดอันดับภายในหน้าต่างของคนคนนั้น
ทุกเทอม normalise เป็น 0..1 ก่อนถ่วงน้ำหนัก
detector ที่ไม่มี confidence → ถอดน้ำหนักนั้นทิ้งแล้วหารใหม่ (ไม่เติมค่ากลาง)
```

> Laplacian ไม่มีเพดาน ส่วน ratio กับ confidence เป็นเศษส่วน ถ้าไม่ normalise sharpness จะกลบอีกสี่ตัวไปสามหลัก
> และถ้าเติมค่ากลางแทนการถอดน้ำหนัก ทั้ง backend จะโดนหักแต้มคงที่ด้วยเหตุผลที่ไม่เกี่ยวกับรูป

ปลายทาง          DCIM/AutoBots/v0_1_6_yyyyMMdd_HHmmss/

## Upload Pipeline

pipeline ที่ถ่ายรูปไม่ upload เอง — มันแค่ **บอกว่ามีรูปใหม่** แล้วจบหน้าที่
งาน upload ทั้งหมดอยู่คนละเส้นทาง ไม่มีใครในเส้นทาง capture → extract → deliver รู้ว่ามีคลาวด์อยู่

---

### 1. เข้าคิว

```
เข้าคิวเมื่อ       รูป publish ลง MediaStore สำเร็จแล้วเท่านั้น
เก็บอะไร         content:// URI ของ MediaStore  ไม่ใช่ path ในไฟล์ระบบ
กันซ้ำด้วย        relativeKey = {sessionId}/{fileName} · unique
                 enqueue ซ้ำจึงไม่ทำอะไรเลย (idempotent)
```

> cache JPEG ถูกลบทิ้งทันทีหลัง publish — สำเนาเดียวที่เหลือคือรูปในแกลเลอรีของ operator
> ซึ่งเขาลบทิ้งเมื่อไหร่ก็ได้ ระบบจึงต้องอ่านกรณีนั้นเป็น "เลิกลอง" ไม่ใช่ "เน็ตมีปัญหา"

---

### 2. Room Database — 6 สถานะ

```
Pending      เข้าคิวแล้ว ยังไม่เคยลอง
Uploading    worker ถืออยู่ · ค้างสถานะนี้ตอนเปิดแอป = รอบก่อนถูกฆ่ากลางคัน
Uploaded     bytes ถึงที่เก็บแล้ว แต่ backend ยังไม่รู้
Success      backend บันทึก metadata แล้ว — จบ
Failed       ล้มแบบที่ลองใหม่แล้วมีโอกาสรอด (5xx · timeout · เน็ตหลุด)
Abandoned    ล้มแบบที่ลองใหม่ก็ไม่ช่วย (รูปหายจากแกลเลอรี · 4xx ถาวร · ครบ 8 ครั้ง)
```

> Flow v1 มี 4 สถานะ · เราเพิ่มสองตัวที่ตกหล่นบ่อยที่สุดและสำคัญที่สุด
> **`Uploaded`** แยก *"ไฟล์ถึงที่เก็บ"* ออกจาก *"backend รู้แล้ว"* — ถ้าไม่มี ตอน complete พลาด
> ระบบจะแยกไม่ออกจาก PUT พลาด แล้วส่งไฟล์ทั้งก้อนใหม่ หรือแย่กว่านั้นคือทิ้ง object ที่ไม่มี metadata ชี้ถึง
> **`Abandoned`** แยก *"ไว้ค่อยลองใหม่"* ออกจาก *"ลองไปก็เท่านั้น"* — ถ้าไม่มี รูปที่ operator ลบไปแล้ว
> จะค้างใน Failed แล้วกินแบตวนไปเรื่อย ๆ

---

### 3. WorkManager

```
งาน              unique work 1 ตัว ระบายทั้งคิว  (ไม่ใช่ 1 งานต่อ 1 ไฟล์)
เงื่อนไขเริ่ม       มีเน็ต (Wi-Fi หรือ 4G ก็ได้) · แบตไม่ต่ำ
ขณะทำงาน        เลื่อนเป็น foreground service
claim ทีละ       20 แถว · หมดแล้วขอชุดใหม่ · ไม่มีของค้างแล้วหยุด
ตอนเริ่มรอบ       รีเซ็ตแถวที่ค้าง Uploading จากรอบก่อนก่อนเสมอ
หยุดชั่วคราวได้    operator กดได้ · ตัวที่กำลังส่งค่อยส่งจนจบ
```

> **1 งานต่อ 1 ไฟล์คือกับดัก** — session เดียวจะยัดหลายร้อยแถวลงตาราง `WorkSpec` ของระบบ
> ไม่มีลำดับ และจ่ายค่า scheduler ทุก ๆ JPEG 800 KB
> ส่วน foreground service คือสิ่งที่ซื้อเน็ตกับ CPU ตอนเครื่องพักจอ — ไม่มีมันแล้ว Doze จะฆ่างานทิ้งกลางคิว

---

### 4. เส้นทางต่อ 1 รูป

```
ขอ presigned URL      GraphQL mutation → ได้ key + URL ที่ server เป็นคนตั้งชื่อ
        ↓
PUT ขึ้น storage      อ่าน bytes จาก content:// สตรีมตรง ไม่โหลดทั้งไฟล์เข้า RAM
        ↓
mark Uploaded         ← จุดตัด: ก่อนบรรทัดนี้ retry = ส่งไฟล์ใหม่
                         หลังบรรทัดนี้ retry = ส่งแค่ complete
        ↓
complete → backend    backend บันทึก metadata
        ↓
mark Success          จบ · ไฟล์ในเครื่องยังอยู่ครบ
```

> แถวที่ค้างสถานะ `Uploaded` ตอนรอบถัดไปมาเจอ จะ**ข้าม PUT ไปเลย** ยิงแค่ complete ซ้ำ
> นี่คือเหตุผลเดียวที่สถานะนั้นมีอยู่

---

### 5. เมื่อพัง

```
แยกความผิดพลาดเป็น 3 แบบ
  Retryable      5xx · timeout · เน็ตหลุด        → Failed แล้วนับถอยหลังรอ
  Permanent      รูปหาย · 4xx ถาวร              → Abandoned ทันที ไม่นับ attempt
  Unauthorized   token ใช้ไม่ได้                  → หยุดทั้งคิว ไม่ใช่แค่รูปนี้

backoff ต่อแถว   30 วิ → คูณสอง → เพดาน 30 นาที
เลิกลองเมื่อ      ครบ 8 ครั้ง
backoff ของงาน   30 วิ exponential (คนละชั้นกับ backoff ต่อแถว)
```

> **backoff อยู่ที่แถว ไม่ใช่แค่ที่งาน** — รูปเสียหนึ่งรูปต้องไม่ฉุดทั้งคิว
> และค่านี้อยู่ในฐานข้อมูล จึงรอด reboot ซึ่ง backoff ของ WorkManager เองทำไม่ได้ในระดับแถว
> **`Unauthorized` หยุดทั้งคิว** เพราะมันไม่เคยเป็นเรื่องของรูปใบเดียว — ทุกแถวที่เหลือจะพังแบบเดียวกัน
> และบน backend ที่ presign ไม่ต้อง auth มันจะโผล่ตอน complete คือ**หลังส่งไฟล์ไปหมดแล้ว**

---

### 6. ตั้งค่าเครื่อง

```
สแกน QR         ได้ endpoint + platform มาทั้งชุด ไม่ต้องพิมพ์
ล็อกอิน          ได้ token
เลือก event      จากรายการที่ backend ส่งมา ไม่ต้องพิมพ์ MongoID 24 ตัว
```

> สองค่าที่ไม่ควรมีใครต้องพิมพ์บนมือถือหน้างานคือ bearer token กับ event id — ตัดออกทั้งคู่

---

### ※ ไม่ลบไฟล์ในเครื่อง ไม่ว่ากรณีใด

Flow v1 เขียนไว้ว่า `Delete Local File (optional)` — ของเรา**ตัดออกทั้งข้อ ไม่มี toggle ด้วยซ้ำ**

upload คือการ **คัดลอก** ขึ้นคลาวด์ ไม่ใช่การ **ย้าย**
ถ้าอัปสำเร็จแต่ backend มีปัญหาทีหลัง รูปงานที่ถ่ายมาทั้งวันจะไม่มีทางกู้กลับมาได้เลย
พื้นที่ในเครื่องถูกกว่างานที่ถ่ายใหม่ไม่ได้

---

## Backend Flow

**เราไม่ได้ทำ backend เอง** — ต่อกับแพลตฟอร์มที่มีอยู่แล้ว ไม่มี Hono / Workers / R2 ในโปรเจกต์นี้
ฝั่งแอปรู้จัก backend ผ่าน [`UploadTransport`](../androidApp/src/main/kotlin/com/autobots/camera/upload/UploadTransport.kt) อินเทอร์เฟซเดียว
ทั้งคิว worker และ 6 สถานะ ถูกสร้างและพิสูจน์กับ transport ปลอมมาก่อน แล้วค่อยเสียบตัวจริงเข้าไป

```
3 host คนละที่กัน — ไม่ใช่ backend เดียว

Runx GraphQL          ขอ signed URL
Google Cloud Storage  รับ bytes
แพลตฟอร์ม (REST)      รับ metadata
```

---

### Step 0 — ตั้งค่าเครื่อง (ทำครั้งเดียว)

```
Android → GraphQL     mutation authAdminUser(username, password)
        ←             token

Android → GraphQL     query eventItems
        ←             รายการ event ให้เลือก
```

> ทำเพื่อไม่ให้ใครต้องพิมพ์ bearer token หรือ event id 24 ตัวบนมือถือหน้างาน
> ส่วน endpoint กับ platform มาจากการสแกน QR

---

### Step 1 — ขอ signed URL

```
Android → GraphQL     mutation photoUpload
                        provider  "gs"
                        mimeType  "image/jpeg"

Authorization         ไม่ส่ง — ตามที่ client ตัวที่รันอยู่ production ทำอยู่
```

> Flow v1 ส่ง Device ID + Capture Time ตอน presign · ของจริงไม่รับสองค่านี้
> capture time เก็บไว้ในคิวฝั่งเราและส่งตอน complete แทน

---

### Step 2 — backend ตอบกลับ

```
        ←             uploadUrl    URL ที่ signed แล้ว
                      downloadUrl  URL ปลายทางของ object

key                   แกะจาก downloadUrl (segment แรกคือ bucket ที่เหลือคือ key)
expire time           ไม่ส่งกลับมา — อายุฝังอยู่ใน signature
```

> **object key ไม่ deterministic** — server เป็นคนตั้งชื่อไฟล์เอง (UUID) เราเดาล่วงหน้าไม่ได้
> Flow v1 สมมติว่าเราเป็นคนตั้ง key ได้ ซึ่งใช้ไม่ได้ที่นี่
> นี่คือเหตุผลที่แถวในคิวต้องมีคอลัมน์ `remoteKey` / `remoteUri` — ถ้าไม่เก็บค่าที่ตอบกลับมา
> แถวที่ค้างสถานะ `Uploaded` จะไม่มีวันจบได้ เพราะ bytes อยู่ใน bucket โดยไม่มีใครเรียกชื่อมันถูก

---

### Step 3 — PUT ขึ้น storage

```
Android → GCS         PUT uploadUrl
Content-Type          image/jpeg  ต้องตรงกับที่ signed ไว้ เป๊ะ ๆ
Content-Length        ความยาวจริงของ bytes ที่จะส่ง
```

> อ่านไฟล์เข้า memory ก่อนส่ง เพื่อให้ `Content-Length` เป็นค่าจริงไม่ใช่ค่าที่เดาจากแถวในคิว
> signed PUT ที่ความยาวไม่ตรงกับตัวเอง จะพังในแบบที่อ่าน error ไม่รู้เรื่อง
> ทีละรูป ๆ ละไม่กี่ MB — worker ไม่เคยถือสองรูปพร้อมกัน

---

### Step 4 — บอกแพลตฟอร์มว่ามีรูปแล้ว

```
Android → แพลตฟอร์ม   POST  (form-urlencoded)
                        eventId
                        key      key ที่ server ตั้งให้
                        name     ชื่อไฟล์เดิมของเรา
                        uri      downloadUrl

Authorization         Bearer token  ← ขั้นตอนเดียวที่ใช้ token
```

> เรียกซ้ำได้โดยไม่พัง (idempotent by contract) — คิวพึ่งข้อนี้ในการปิดแถวที่ bytes ขึ้นไปแล้ว
> แต่รอบก่อนตายก่อนจะ complete
> `name` ส่งไปเพื่อให้แพลตฟอร์มแสดงชื่อที่คนอ่านออก แทน UUID ที่ server ตั้ง

---

### ข้อควรรู้ — token ใช้ตอนท้าย ไม่ใช่ตอนต้น

```
Step 1  presign     ไม่ใช้ token
Step 3  PUT         ไม่ใช้ token (signature เป็นตัวรับรอง)
Step 4  complete    ใช้ token  ← token เสียจะรู้ตรงนี้
```

> แปลว่า token หมดอายุ **จะไม่โผล่จนกว่าไฟล์จะส่งขึ้นไปหมดแล้ว**
> ถ้าปล่อยให้ retry ตามปกติ ทั้งคิวจะอัปโหลดจนครบทุกไฟล์เพื่อไปโดนปฏิเสธทีละใบ
> `UploadException.Unauthorized` จึง **หยุดทั้งคิว** ไม่ใช่แค่ทำให้รูปใบนั้นล้ม

---

### Error Handling

```
Retryable       5xx · timeout · เน็ตหลุด    → Failed · backoff 30 วิ ×2 เพดาน 30 นาที
Permanent       รูปหายจากแกลเลอรี · 4xx     → Abandoned ทันที
Unauthorized    token ใช้ไม่ได้              → หยุดทั้งคิว

ไม่มีเน็ต        คิวอยู่ใน Room · WorkManager ปลุกให้เองเมื่อเน็ตกลับมา
เลิกลอง          ครบ 8 ครั้ง
```

> รายละเอียดอยู่ที่ [Upload Pipeline](#upload-pipeline) ข้อ 5 — ตรงนี้เขียนไว้เพื่อให้อ่านจบในหน้าเดียวได้

## Performance Requirements

ตัวเลขในหัวข้อนี้แบ่งเป็นสองแบบ — **ค่าที่ตั้งไว้** (เปลี่ยนได้ในโค้ด) กับ **ค่าที่วัดมาแล้ว** (เปลี่ยนไม่ได้ด้วยการเถียง)
Flow v1 กำหนดไว้แต่แบบแรก เอกสารนี้แยกให้ชัดว่าอันไหนคืออันไหน

---

### ตัวชี้วัดหลัก — `realtimeRatio`

```
นิยาม            เวลาที่ใช้ประมวลผล ÷ ความยาวคลิป

< 1.0            ประมวลผลเร็วกว่าที่กล้องถ่าย → ถ่ายสดได้ไม่จำกัดเวลา คิวไม่บวม
= 1.0            พอดีเป๊ะ ไม่มีที่เหลือ
> 1.0            ช้ากว่าที่ถ่าย → ถ่ายสดนาน ๆ คิวบวมจนกล้องต้องหยุดรอ

วัดล่าสุด         0.502   (4K · Face · NPU · Xiaomi peridot)
เส้นทางที่มา      v0.1.3  2.196
                 v0.1.4  1.010   ← ข้ามเส้น 1.0 ครั้งแรก
                 v0.1.5  0.502
```

> Flow v1 วัดด้วย **Detection FPS** ซึ่งเป็นตัวเลขของ pipeline แบบ real-time
> ของเราไม่มีค่านั้นให้วัด เพราะไม่ได้ตรวจจับสด — สิ่งที่ต้องรู้คือ **ตามทันกล้องไหม** ซึ่งคือ ratio นี้
> ต่ำกว่า 1.0 คือเงื่อนไขเดียวที่ทำให้ "อัดต่อเนื่องหลายชั่วโมง" เป็นไปได้ ไม่ใช่ FPS

---

### ค่าที่ตั้งไว้

```
Recording Resolution    1920x1080  หรือ  3840x2160
Preview                 30 FPS
Sample Interval         120 ms      (ทั้ง FHD และ 4K)
Detect Bitmap           640 px กว้าง
Detect Workers          2 เธรด
Frame Queue             6
Video Queue             8 chunk
Chunk Size              50 MB
Output                  JPEG 95 · ความละเอียดเต็มของเฟรมวิดีโอ
Upload                  1 worker · claim ทีละ 20 แถว
```

> **JPEG 95 ไม่ใช่ 90–95** — เลือกค่าเดียวไปเลย เพราะค่าที่แกว่งทำให้เทียบขนาดไฟล์ข้าม session ไม่ได้
> **Detect Workers = 2** คือสิ่งที่พา ratio จาก 1.430 ลง 1.010 — decode กับ detect เคยรันเรียงกันทั้งที่เครื่องมี 8 คอร์

---

### ค่าที่วัดมาแล้ว

```
4K · 507 เฟรม · Xiaomi peridot

yuv_nv21          9.5 ms/เฟรม     ← เคย 63.9 · แก้ลูปที่วน 2 ล้านรอบต่อเฟรม
worker_idle       27.5 ms/เฟรม    ← เคย 109.6
wall (process)    29,917 ms       ← เคย 52,486
kept              15 รูป          ← เท่าเดิมเป๊ะ ทั้งที่เร็วขึ้น 43%

detect (median)   NPU เร็วกว่า GPU 14 ms · ชนะใน 877/986 เฟรม
GPU warm-up       เฟรมแรกของ session จ่าย 2.5 วินาที (shader compile)
```

> **`kept` เท่าเดิมเป๊ะคือส่วนที่สำคัญที่สุดในตารางนี้** — เร็วขึ้น 43% โดยได้รูปชุดเดิม
> แปลว่าแก้ที่ต้นทุน ไม่ได้แก้ด้วยการทำงานน้อยลง ถ้า `kept` ขยับด้วย ตัวเลขความเร็วจะไม่มีความหมาย

### Thermal

```
ตอนนี้            แสดงผลอย่างเดียว ไม่ลดงานอัตโนมัติ
วัดอะไร           thermal status · headroom · CPU · RAM · power ต่อรูป
บันทึกที่          perf_report.json + ขึ้นบนจอตอนรัน
```

> เหตุผลเดิมที่ไม่ทำ auto-throttle คือ *"ลดงานเงียบ ๆ แล้วจะพลาดนักวิ่ง"* ซึ่งจริงกับ pipeline แบบ real-time
> **แต่ใช้ไม่ได้กับ pipeline นี้** — วิดีโอถูกอัดไว้หมดแล้ว การยืด sample interval หรือหยุด upload ชั่วคราว
> ไม่ทำให้พลาดใครเลย แค่ทำให้ backlog ยาวขึ้น ข้อนี้จึงควรเปลี่ยนสถานะจาก "ตั้งใจไม่ทำ" เป็น "ยังไม่ได้ทำ"

งานยาว 4 ชั่วโมง       ที่ผ่านคือ Doze ที่บังคับเอง 4 นาทีครึ่ง

                      อัตราการล้มของ PUT บน 4G ยังไม่มีตัวเลข
เพดาน dataSync        Android 14+ จำกัด 6 ชม./วัน · ยังไม่รู้ว่าชนเมื่อไหร่
