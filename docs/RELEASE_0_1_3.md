v0.1.2 **ประมวลผล UHD ช้ากว่าเวลาจริง 2.35 เท่า** และเก็บได้ **3 รูปจาก 507 เฟรม** ที่ sample มา

การวัดด้วย `perf_report.json` ชี้ว่าสาเหตุไม่ใช่สิ่งที่คาดกันไว้:

**65.6% ของเวลาทั้งหมดหมดไปกับการแปลงฟอร์แมตภาพ** และรูปที่หายไปเกือบทั้งหมดถูกตัดด้วย**เกณฑ์ขนาดใบหน้า** ไม่ใช่คุณภาพ

## การเปลี่ยนแปลง

### 1. Decode ลง Surface — **ปิดไว้ ยังใช้ไม่ได้**

**ไฟล์:** [VideoFrameSampler.kt](../androidApp/src/main/kotlin/com/autobots/camera/pipeline/VideoFrameSampler.kt) · ค่าคงที่ `SURFACE_DECODE_ENABLED = false`

> **บันทึกความล้มเหลว** — ส่วนนี้เขียนเสร็จ ทดสอบบนเครื่องจริง แล้ว**ไม่ผ่าน** เก็บโค้ดไว้แต่ปิดสวิตช์ เพราะข้อมูลที่ได้มีค่าสำหรับความพยายามครั้งหน้า
>
> ```
> surface_rgba   216   250.2ms   253.0ms   54036.8ms   ← timeout ทุกเฟรม สำเร็จ 0
> REALTIME RATIO 8.62x
> ```
>
> `c2.qti.avc.decoder` (Qualcomm, Android 16) **ไม่เรนเดอร์ลง `ImageReader` แบบ `RGBA_8888`** — สมมติฐานตั้งต้นผิด hardware video decoder ไม่รองรับฟอร์แมตนี้เป็น consumer surface
>
> ที่แย่กว่านั้นคือ fallback เดิมรอ 250 ms ต่อเฟรม **ทุกเฟรม ทุก chunk** = เสียเปล่า 54 วินาที/chunk ทำให้ ratio แย่ลงจาก 2.35× เป็น **8.62×** — แย่กว่าไม่แก้เลย
>
> **บทเรียนที่แก้เชิงโครงสร้างแล้ว:** ตอนนี้มี probe หยุดหลัง 3 เฟรม (`SURFACE_PROBE_FRAMES`) และจำผลไว้ทั้ง process (`surfaceUnsupported`) — เดาผิดครั้งหน้าจะเสียเวลา ~360 ms ครั้งเดียว ไม่ใช่ 54 วินาทีต่อ chunk
>
> **ทางที่ถูกสำหรับครั้งหน้า:** `ImageFormat.PRIVATE` + `HardwareBuffer.USAGE_GPU_SAMPLED_IMAGE` + `Bitmap.wrapHardwareBuffer()` (API 29+) โดยต้องจัดการให้ `Image` มีอายุยืนกว่าทุก Bitmap ที่แตกออกมาจากมัน — เป็นคนละดีไซน์ ต้องทดสอบบนเครื่องก่อนเปิดใช้

**ปัญหาที่ยังรออยู่** — v0.1.2 แปลงทุกเฟรมแบบนี้:

```
MediaCodec → YUV_420_888 → NV21 (วน loop ต่อ pixel ใน Kotlin)
           → JPEG encode 92% → JPEG decode → Bitmap ARGB_8888
```

encode JPEG แล้ว decode กลับทันที **เพื่อให้ได้ Bitmap เฉยๆ** ที่ UHD ราคา 123.6 ms ต่อเฟรม

**การแก้** — ให้ decoder เรนเดอร์ลง `ImageReader` แบบ RGBA_8888 โดยตรง:

```kotlin
val reader = ImageReader.newInstance(width, height, PixelFormat.RGBA_8888, 3)
decoder.configure(format, reader.surface, null, 0)
...
decoder.releaseOutputBuffer(outputIndex, wanted)  // wanted=false → ทิ้งฟรี
```

**ทำไมถึงดีกว่า**

1. **การแปลง YUV→RGB ย้ายไปอยู่บน display pipeline** ไม่กิน CPU
2. **เฟรมที่ไม่ได้ sample ไม่เสียค่าอะไรเลย** — v0.1.2 เรียก `getOutputImage()` ทุกเฟรมแล้วค่อยทิ้ง ส่วน v0.1.3 สั่ง `releaseOutputBuffer(index, false)` จบ
3. **ภาพคมขึ้นจริง** — v0.1.2 บีบ JPEG **สองรอบ** (92% ตอน sample → 95% ตอน save) ตัดรอบแรกออกแล้วรูปที่ส่งมอบเสียคุณภาพน้อยลง และ `FaceSharpnessScorer` ก็วัดจากภาพที่ไม่ถูก JPEG ทำให้ขอบเบลอ → คะแนนตรงความจริงขึ้น

`yuv_jpeg_argb` จึงยัง**เป็น 46% ของเวลาอยู่เหมือนเดิม** ใน v0.1.3 — ยังไม่ได้แก้ เป็นงานค้างชิ้นใหญ่ที่สุด

เส้นทางที่ใช้จริงบันทึกไว้ใน `perf_report.json` ฟิลด์ `chunks[].decodePath` (ตอนนี้จะเป็น `"yuv"` เสมอ)

### 2. หมุนภาพตอนที่ยังเล็ก ไม่ใช่ตอน 4K

**ไฟล์:** [VideoFrameSampler.kt](../androidApp/src/main/kotlin/com/autobots/camera/pipeline/VideoFrameSampler.kt) · [VideoFrameProcessor.kt](../androidApp/src/main/kotlin/com/autobots/camera/pipeline/VideoFrameProcessor.kt)

**ปัญหา** — วิดีโอที่ถ่ายแนวตั้งมี `rotationDegrees: 90` v0.1.2 หมุน**ทุกเฟรมที่ความละเอียดเต็ม** ก่อนส่งต่อ:

```
4K (8.3M pixels) → rotate 90° → scale 640 → detect
                   ↑ 52 ms/เฟรม
```

**การแก้** — สลับลำดับ และเลื่อนการหมุนเต็มไปให้หลังสุด:

```
4K → scale (คำนวณให้ผลลัพธ์หลังหมุนกว้าง 640) → rotate 640px → detect
                                                  ↑ ~5 ms/เฟรม

เฟรมที่ผ่านด่านขนาดแล้วเท่านั้น → rotate 4K (52 ms × ~9 เฟรม แทน × 507)
```

**ทำไมถึงดีกว่า**

- Sampler ส่งเฟรมออกมาแบบ **ยังไม่หมุน** พร้อมค่า rotation แล้วให้ Processor ตัดสินว่าจุดไหนถูกที่สุด
- **ML Kit เห็นภาพเดิมทุกประการ** — จงใจคำนวณ scale factor จากด้านกว้าง*หลังหมุน* เพื่อให้ detect bitmap ออกมาขนาดเท่า v0.1.2 เป๊ะ (640 × 1138) ถ้า scale ตรงๆ แล้วค่อยหมุนจะได้ 360 × 640 ซึ่งหน้าคนจะเล็กลงและตรวจเจอน้อยลง
- ด่านขนาดตัดสินใน detect space ทำให้ **เฟรมที่ถูกตัดไม่ต้องจ่ายค่าหมุน 4K เลย**
- Live capture ไม่กระทบ — chunk ที่อัดเองรายงาน rotation 0 อยู่แล้ว เส้นทางนี้ข้ามไปทั้งหมด

### 3. ลดเกณฑ์ขนาดใบหน้า — และปลดล็อก ML Kit ด้วย

**ไฟล์:** [VideoFrameProcessor.kt](../androidApp/src/main/kotlin/com/autobots/camera/pipeline/VideoFrameProcessor.kt) · [OfflineFaceDetector.kt](../androidApp/src/main/kotlin/com/autobots/camera/detection/OfflineFaceDetector.kt)

```kotlin
// VideoFrameProcessor
MIN_FACE_HEIGHT_RATIO  0.05f  →  0.035f

// OfflineFaceDetector
setMinFaceSize(0.05f)  →  setMinFaceSize(0.025f)
```

**ทำไมต้องแก้สองที่** — นี่คือจุดที่พลาดได้ง่ายที่สุด ระบบมีด่านขนาด **สองชั้น** ที่ตั้งไว้ 0.05 เท่ากันโดยบังเอิญ:

| ด่าน | อยู่ที่ไหน | เทียบกับอะไร |
|--|--|--|
| `setMinFaceSize` | ภายใน ML Kit | **ความกว้าง** ของภาพ |
| `MIN_FACE_HEIGHT_RATIO` | โค้ดเรา | **ความสูง** ของภาพ |

ถ้าลดแค่ตัวหลัง ML Kit จะยัง**ไม่รายงานหน้าที่เล็กกว่าเกณฑ์ของมันเองตั้งแต่แรก** → เฟรมนั้นถูกนับเป็น `no_subject` ไม่ใช่ `too_small` และการลดเกณฑ์ก็ไม่มีผล

**ทำไมถึงดีกว่า** — จากข้อมูลจริง 42 จาก 96 เฟรมที่ถูกตัดมี `subjectRatio ≥ 0.035` คือ**นักวิ่งที่กำลังวิ่งเข้ามา แต่ถูกตัดก่อนถึงระยะ**

**ผลที่วัดได้** — ตรงตามที่ออกแบบ:

```
tooSmall  96 → 50   (−46)
candidate  9 → 42   (+33)
tooSoft    0 → 11   (+11)        33 + 11 = 44 ≈ 46 ✓
```

**แต่การแก้ `setMinFaceSize` ไม่มีผลเลย** — เอกสารฉบับแรกยืนยันว่าต้องลดด้วย ไม่งั้น ML Kit จะกรองหน้าเล็กทิ้งก่อน ข้อมูลบอกว่าไม่จริง:

```
noSubject  402 → 404      ← ML Kit เจอหน้าในเฟรมชุดเดิมเป๊ะ
```

ด่านสองชั้นมีอยู่จริง แต่ที่ระยะเหล่านี้ **`MIN_FACE_HEIGHT_RATIO` เป็นตัวบีบเพียงตัวเดียว** ค่า `setMinFaceSize = 0.025` คงไว้เพราะไม่มีโทษ แต่ไม่ใช่ต้นเหตุของผลที่ได้

**ผลข้างเคียงที่วัดแล้ว** — `sharpness` + `rotate` ถูกเรียกบ่อยขึ้น (n=9 → 53) แต่รวมกันเพียง 2.5% ของเวลา ไม่กระทบ realtimeRatio

### 4. เลือก hardware decoder ให้ถูกต้อง

**ไฟล์:** [VideoFrameSampler.kt](../androidApp/src/main/kotlin/com/autobots/camera/pipeline/VideoFrameSampler.kt)

v0.1.2 หา hardware decoder ด้วยการดูว่าชื่อ codec มี `"omx"` หรือ `"hw"` — แต่ Android สมัยใหม่ใช้ Codec2 ที่ชื่อเป็น `c2.qti.avc.decoder` (hardware) กับ `c2.android.avc.decoder` (**software**) ซึ่งไม่เข้าเงื่อนไขทั้งคู่ → คืน `null` เสมอ และ log ขึ้นว่า "using software" ทั้งที่ fallback มักได้ hardware มาอยู่ดี

v0.1.3 ใช้ `MediaCodecInfo.isHardwareAccelerated()` บน API 29+ (ยังคง heuristic เดิมไว้สำหรับ API 26–28)

ผลด้านความเร็วน้อย (decode เป็น 0.13% อยู่แล้ว) แต่ทำให้ **log พูดความจริง** และปิดความเสี่ยงที่จะไปได้ software codec บนเครื่องบางรุ่น

### 6. Dedup เก็บ top-3 ต่อ window

**ไฟล์:** [VideoFrameProcessor.kt](../androidApp/src/main/kotlin/com/autobots/camera/pipeline/VideoFrameProcessor.kt) — `MAX_KEEP_PER_WINDOW = 3`

**ทำไมถึงเข้ามาในรอบนี้** — เดิมตั้งใจเลื่อนออกไป แต่การวัดหลังแก้ข้อ 3 เปลี่ยนภาพทั้งหมด:

```
candidate 42  →  kept 7      ทิ้งไป 83%
```

ตอน v0.1.2 มี candidate แค่ 9 ตัว dedup จะเก็บกี่ตัวก็ไม่ต่างกันนัก พอเปิดด่านขนาดแล้วมี 42 ตัว **dedup กลายเป็นตัวจำกัดหลักแทน**

ตัวอย่างจริง — นักวิ่งคนหนึ่งใน chunk 5 candidate ติดกัน 16 เฟรม (5.04–6.84 วิ) sharpness สูงสุด 616 ได้ออกมา 3 รูป เพราะกติกาเดิมให้ **1 รูปต่อ 1 วินาที** ขัดกับ **Keep-All Policy** ใน [CONTEXT.md](../CONTEXT.md) ที่ระบุว่า Passage Outcome ควรได้ ~3 รูปต่อคน

**ปัญหา memory ที่เคยเป็นเหตุผลให้เลื่อน — แก้ได้ด้วยการสลับลำดับ**

เดิมกังวลว่าการจัดอันดับ top-N ต้องถือ Bitmap 4K หลายใบ (~33 MB/ใบ) ทางออกคือ**เขียน JPEG ทันทีที่เป็น candidate แล้วค่อยจัดอันดับจากไฟล์**:

```
เดิม:  ถือ Bitmap ที่คมสุดไว้ 1 ใบ → ปิด window → เขียน 1 ไฟล์
ใหม่:  เขียนทุก candidate ทันที (recycle bitmap) → ปิด window → เก็บ 3 ไฟล์ ลบที่เหลือ
```

memory คงที่ที่ 1 bitmap ไม่ว่า window จะมีกี่เฟรม ต้นทุนคือ `save_jpeg` ~83 ms × 42 candidate ≈ **3.5 วินาที (3% ของ runtime)** — ราคาถูกมากเพราะ candidate เป็นเฟรมที่ผ่านมาแล้วสองด่าน มีเพียง 8% ของเฟรมทั้งหมด

พร้อมกันนี้ขยาย `IMAGE_QUEUE_CAPACITY` **16 → 48** เพราะไฟล์ต่อ chunk เพิ่มขึ้นราว 3 เท่า และ WriteQueue ที่เต็มจะ **drop รูปเงียบๆ**

### 7. Clamp ROI — แก้บั๊ก `sharpness = 0`

**ไฟล์:** [VideoFrameProcessor.kt](../androidApp/src/main/kotlin/com/autobots/camera/pipeline/VideoFrameProcessor.kt) — `mapRect()` · `isUsableRoi()`

ข้อมูลจากการวัดพบ 4 เฟรมได้คะแนน **0 พอดี** ทั้งที่ subject ใหญ่พอ:

```json
{ "ptsUs": 2520000, "outcome": "too_soft", "sharpness": 0, "subjectRatio": 0.044 }
```

`subjectRatio 0.044` = หน้าสูง ~169 px ในภาพเต็ม ใหญ่เกินกว่าจะวัดไม่ได้ สาเหตุคือ `FaceSharpnessScorer` คืน `0.0` เมื่อ ROI กว้างหรือสูง < 8 px ซึ่งเกิดเมื่อ **กล่องที่ map แล้วตกนอกขอบภาพ** — ML Kit ที่เปิด `enableTracking()` คืนกล่องที่ล้ำขอบเฟรมได้เมื่อคนอยู่ริมภาพ

ผลคือเฟรมถูกตัดด้วยเหตุผล **"เบลอ"** ทั้งที่ความจริงคือ **"วัดไม่ได้"** — คนละเรื่องกัน และทำให้สถิติ `tooSoft` ปนเปื้อน

**การแก้** — `mapRect` clamp พิกัดเข้าขอบภาพ แล้วเพิ่มการตรวจ `isUsableRoi()` เฟรมที่ ROI ใช้ไม่ได้จะนับเป็น **`roiInvalid`** แยกออกมา ไม่ปนกับ `tooSoft` อีก (มีทั้งใน `perf_report.json` และ log)

### 8. 🐛 Session ที่ chunk สุดท้ายมีรูป จะไม่เขียน log เลย

**ไฟล์:** [WriteQueue.kt](../androidApp/src/main/kotlin/com/autobots/camera/delivery/WriteQueue.kt)

**อาการ** — import ไฟล์ 4 นาที ได้รูป 158 ใบใน `DCIM/AutoBots/ext_11082026_1134/` แต่**ไม่มี `session_log.txt` และไม่มี `perf_report.json` เลย** ทั้งใน `Download/` และ cache mirror ประมวลผลครบ 36 chunk เรียบร้อย ไม่มี error

**สาเหตุ** — ลำดับใน worker loop ผิด:

```kotlin
val uri = writer.publish(file)
if (uri != null) {
    …
    onDelivered(uri)        // ← เรียก maybeNotifyDrainComplete() ตรงนี้
}
…
finally { pending.decrementAndGet() }   // ← ตัวนับเพิ่งลดหลังจากนั้น
```

`maybeNotifyDrainComplete()` เช็ค `isBusy()` ซึ่งดู `imageDelivery.pendingCount` ตอนที่ callback ทำงาน **ไฟล์ใบสุดท้ายยังถูกนับว่า pending อยู่** → `isBusy()` = true → return ทันที แล้วหลังจากนั้นไม่มีใครเรียก `maybeNotifyDrainComplete()` อีกเลย

**ทำไมเพิ่งโผล่** — บั๊กนี้มีมาตั้งแต่ v0.1.2 แต่จะกระตุ้นก็ต่อเมื่อ **chunk สุดท้ายมีรูปที่เก็บได้** ในการทดสอบไฟล์ 1 นาทีทุกรอบ chunk สุดท้าย `kept = 0` พอดี (เป็นเศษวิดีโอท้ายคลิปที่ไม่มีคน) จึงรอดมาตลอด

การแก้ [ข้อ 6](#6-dedup-เก็บ-top-3-ต่อ-window) เพิ่มโอกาสที่ chunk ใดๆ จะมีรูปขึ้นราว 3 เท่า — **ไม่ได้สร้างบั๊ก แต่ทำให้มันกลายเป็นเรื่องปกติแทนที่จะเป็นเรื่องบังเอิญ**

**การแก้** — เลื่อน callback ไปหลัง `pending.decrementAndGet()` เพื่อให้ตัวนับที่ผู้เรียกใช้ตัดสินใจสะท้อนความจริง

> **สิ่งที่บั๊กนี้สอน** — โค้ดที่แก้ในข้อ 6 ไม่ได้ผิด แต่มันไปเปลี่ยน**ความถี่ของเงื่อนไข**ที่บั๊กเดิมรออยู่ ผลกระทบไม่ได้อยู่ในไฟล์ที่แก้ และการทดสอบไฟล์ 1 นาทีซ้ำ 3 รอบก็ไม่มีทางเจอ เพราะคลิปนั้นจบด้วย chunk ที่ไม่มีคนพอดีทุกครั้ง

เครื่องมือวัดที่รายงานผิดอันตรายกว่าไม่มีเครื่องมือ สองจุดที่แก้:

### 📏 ฟิลด์ `splitDurationMs` วัดผิดความหมาย

| | run1mins | run4mins |
|--|--|--|
| `splitDurationMs` | 2,912 ms | **455,841 ms** |

remux ไฟล์ 1.93 GB ควรใช้ ~20 วินาที ไม่ใช่ 456 วินาที ดู `events` จะเห็นสาเหตุ:

```
tMs  17,067   chunk 1 process_end
tMs  17,640   chunk 9 queued        ← ผลิต chunk ใหม่ทันทีที่มีที่ว่าง
tMs  33,679   chunk 2 process_end
tMs  34,232   chunk 10 queued
```

splitter ถูก backpressure บีบให้ผลิต **1 chunk ต่อ 1 chunk ที่ประมวลผลเสร็จ** ตลอด session — `videoQueue` ค้างที่ 8/8 ตั้งแต่วินาทีที่ 3.9 ถึงวินาทีที่ 493

**ระบบทำงานถูก** (นี่คือหน้าที่ของ backpressure) แต่ฟิลด์นี้วัด "เวลารวมของ pipeline" ไม่ใช่ "ความเร็ว remux" ในไฟล์ 1 นาทีคิวรับได้ทั้ง 8 chunk เลยไม่ต้องรอ ตัวเลขสองรอบจึง**เทียบกันไม่ได้เลย** — ควรแยกเป็น `splitActiveMs` / `splitBlockedMs` ใน release ถัดไป

### บั๊ก drain — แก้ได้จริง

```
drain complete · trigger=event
```

การแก้ลำดับใน `WriteQueue` ([ข้อ 8](#8--session-ที่-chunk-สุดท้ายมีรูป-จะไม่เขียน-log-เลย)) ทำงานตามที่ออกแบบ — callback ของรูปใบสุดท้ายเป็นตัวจุด drain ไม่ใช่ watchdog

**แต่ยังมีจุดที่อธิบายไม่ได้:** session ก่อนหน้าที่มีตัวแก้นี้แล้วยังเขียน log ไม่สำเร็จ ยังหาสาเหตุที่แท้จริงไม่เจอ — watchdog จึงยังคงอยู่เป็นตาข่ายกันไว้ และบรรทัด `drain blocked` (`worker=true videoPending=1 imageQueue=0`) จะบอกเราทันทีถ้าเกิดขึ้นอีก

## การตรวจสอบหลังติดตั้ง

**ยืนยันครบทุกข้อบนเครื่องจริงแล้ว** — เทียบสิ่งที่ทำนายกับสิ่งที่วัดได้:

| ทำนายไว้ | วัดได้ | |
|--|--|--|
| `save_jpeg` n ≈ จำนวน candidate | **40 = 40 เป๊ะ** | ✓ |
| `rotate` n = เฟรมที่ผ่านด่านขนาด | **55 = candidate 40 + tooSoft 14 + roiInvalid 1** | ✓ |
| ไม่มี `sharpness: 0` เหลืออีก | **ไม่มีเลย** (ต่ำสุด 32.7) | ✓ |
| realtimeRatio ~2.0 | **2.017** | ✓ |
| `imageQueue` ไม่ตัน | สูงสุด 9 | ✓ |
| kept ~20 | **16** | ต่ำกว่าเล็กน้อย |
| `roiInvalid` ~4 | **1** | ทำนายสูงไป |
| `tooSoft` ลดเหลือ ~7 | **14 (เพิ่มขึ้น)** | ✗ ทิศทางผิด |

**`sharpness` n = 54 = candidate + tooSoft** ส่วน `rotate` n = 55 — ต่างกัน 1 พอดีคือเฟรม `roiInvalid` ที่ถูกหมุนแล้วแต่ไม่เคยถึง scorer ตัวเลขสอดคล้องกันเองทุกจุด

**ทำไม `tooSoft` ถึงเพิ่มแทนที่จะลด** — และทำไม `roiInvalid` ได้ 1 ไม่ใช่ 4:

`OfflineFaceDetector` เปิด `enableTracking()` ซึ่งทำให้ผลตรวจจับ **ขึ้นกับประวัติเฟรมก่อนหน้า จึงไม่ deterministic ระหว่างรัน** เฟรมเดียวกันได้ `subjectRatio` ต่างกันคนละรอบ (เช่น chunk 4 ที่ 2.52 วิ: รอบก่อน 0.044 → รอบนี้ 0.034) เฟรมที่เคยได้ `sharpness = 0` สองตัวใน chunk 4 รอบนี้ตกไปเป็น `too_small` ก่อนถึง scorer เลย

**ข้อสรุปเชิงวิธีการ: ตัวเลข reject รายประเภทมี noise ±2–3 ระหว่างรัน อย่าตีความ delta เล็กๆ ว่ามีความหมาย** ตัวที่เชื่อได้คือค่าที่ผูกกับโครงสร้าง (`save_jpeg` n, `rotate` n) และค่ารวมใหญ่ๆ (`kept`, `realtimeRatio`)

**`IMAGE_QUEUE_CAPACITY` 16 → 48 กลายเป็นการเผื่อที่ไม่จำเป็น** — สูงสุดที่วัดได้คือ 9 ค่า 16 เดิมก็พอ ไม่มีโทษแต่ก็ไม่ได้แก้ปัญหาจริง

> **บทเรียนกระบวนการจาก release นี้:** โค้ดที่ compile ผ่านแต่ยังไม่ได้รันบนเครื่อง **ไม่ใช่โค้ดที่ทำงานได้** — Surface path ผ่าน compile และดูถูกต้องทุกบรรทัด แต่ทำให้ระบบช้าลง 3.5 เท่าบนเครื่องจริง งานที่แตะ MediaCodec / ImageReader / ฟอร์แมตภาพ ต้องวัดบนเครื่องก่อน merge เสมอ
